## 1. Bilan de la semaine

Après la remise du cahier, nous avons commencé à remplacer les intentions
d'architecture par un environnement exécutable. Le 28 septembre, le commit
`4a68b17` introduit le socle Aegis Control : Spring Boot, PostgreSQL, Flyway,
le broker MQTT local et les premières fonctions d'identité. Il constitue une
première réalisation logicielle, pas encore un parcours de prêt complet.

Le README de l'API conservé dans ce commit décrit explicitement les limites :
aucun catalogue métier exposé, aucune ingestion MQTT et aucun client Web ou
iOS raccordé à ce stade.

## 2. API, identité et environnement local

Le socle fournit la santé du service, la connexion par comptes préparés et la
lecture du profil connecté : `GET /system/health`, `POST /auth/login` et
`GET /auth/me`, sous `/api/v1`. Les contrôles de rôle et de niveau d'accès
restent côté serveur. Le jeton dure 60 minutes, sans refresh token, conformément
au choix d'authentification déjà établi.

L'API relit l'état du compte pour les requêtes protégées; les clients ne
deviennent donc pas l'autorité sur les droits. Les comptes de démonstration
sont activés explicitement et leurs mots de passe ne sont pas versionnés.

Les migrations `V001` et `V002` installent le socle et les tables initiales.
L'existence de tables de catalogue ne signifie pas que les routes métier
correspondantes sont déjà réalisées. Les tests PostgreSQL disposent de bases
temporaires identifiées, distinctes de la base de développement.

Le broker local est réservé au simulateur isolé. Cette installation ne prouve
ni TLS sur le hub réel ni les échanges physiques avec les cellules.

## 3. Contrats et vérification

Le commit `0da2caf`, également du 28 septembre, clarifie l'accès partagé au
statut d'un casier. Cette correction accompagne la mise en place des règles
d'autorisation : les contrats doivent être suffisamment précis pour que le
code n'invente pas les droits de chaque rôle.

Le README historique fournit les commandes de lancement Docker et de tests
Maven, les précautions sur les volumes et l'isolement des bases. Ce journal
n'attribue pas de nombre de tests réussis au 28 septembre : les traces
consultées ici ne donnent pas de rapport chiffré daté suffisant. La présence
du code et d'une procédure n'est pas assimilée à une nouvelle exécution.

## 4. Répartition, limites et suite

Le travail logiciel suivi par Philippe porte sur le backend et son démarrage.
La conception matérielle de Jimmy reste la référence du prototype; aucune
nouvelle mesure physique datée de cette semaine n'est ajoutée à ce bilan.

La prochaine étape est de raccorder les clients, puis de développer le
catalogue et le simulateur. Le retrait et le retour restent à construire :
une authentification réussie ne confirme aucun mouvement d'équipement.

L'assistance IA intervient dans la préparation et la revue du code et des
documents. Ce bilan ne reconstitue pas le détail des appels d'agents; les
choix, la vérification et l'explication du travail restent à notre charge.
